# GitHub 任务跟踪

用户约定：2026-11-09。较大改版与需要持续跟进的问题使用 `to-tickets` 拆分并在 GitHub 跟踪。仓库通过当前 checkout 的 origin 核实，当前为 `Moosphan/MyDashboard`；使用 `gh` 操作。

## 建立任务

- 先检查已有 issue，读取相关正文与评论，优先沿用已有任务。
- 按 `to-tickets` 提供可独立验收的纵向任务、真实阻塞依赖与验收条件。拆分经用户批准后发布；用户已经明确批准的具体拆分无需重复确认。
- 对多项改版建立一个父 issue，各可执行子任务建立独立 issue。以 GitHub 自动分配的 `#编号` 为真实标识，发布前的草稿编号仅供讨论，不猜测将分配的编号。
- 优先使用 GitHub 原生 sub-issue 关系；每个子 issue 正文也引用父编号。同一父任务下的子任务即兄弟任务，父子关系不等于阻塞关系。
- 真正阻塞的任务使用原生 issue dependencies，正文同时列出 `Blocked by` 编号。接口不可用时在子 issue 正文记录 Parent、Siblings 与 Blocked by，使关系仍可核查。
- 标签词汇见 [triage-labels.md](triage-labels.md)。可执行子任务使用 `ready-for-agent`；有未完成 blocker 的子任务等待其解除。父 issue 用于范围管理，不作为可直接领取的开发任务。
- issue 描述交付行为与验收标准，避免具体文件路径和实现代码。

## 执行与完成

- 从所有 blocker 已完成的子任务开始；开始前读取任务正文、评论与依赖，记录当前处理编号。
- 子 issue 记录已验证的进展、阻塞和相关提交或 PR；完成时附测试或实际输出证据。父 issue 的正文和状态留给用户维护，不自动修改或关闭。
- 提交信息关联子 issue 编号；本地测试通过、已提交和已推送分别说明，不以计划代替结果。

## 小问题例外

局部文案、标签误标或低影响的单点修复，范围明确、可直接验证且无后续协调依赖时，可直接修复并随相关提交说明。涉及数据迁移、多个流程、外部依赖、持续排查或跨轮开发时建立或关联 issue。已有相关 issue 的小修复直接关联，不另建重复任务。
